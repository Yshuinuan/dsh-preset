# 总控（project-manager）Agent 预设

一个只管多会话开发流程的 agent：先读项目材料，再把工作拆成 P，写任务书和开工语；项目出问题时，定位到该改的那个 P，改它的任务书，并写出让你转交的话。

它不写代码、不改项目材料、不做验收，也不直接联系 P。它只拥有任务文档区。

## 它怎么工作

1. **读材料**：先确认项目根（绝对路径）、任务文档区、会话工作区，再列清单，按「策划案/需求/验收标准 > 设计/技术方案 > README/旧文档 > 代码结构」的顺序读；只读，不改。docx/xlsx/pdf 读不了正文时，会向你要 md/txt 导出或关键片段。
2. **提问**：只问影响拆分的事，一次最多 3 个，给选项、代价、推荐。读不了、材料矛盾、范围不清，都会先摆出来。
3. **拆分**：整理「模块 → 需求 → 交付物 → 验收」，再按“一个 P 一个可独立验收的交付物”拆；用 S/M/L + 不确定度估工作量，给推荐会话数，以及 N-1 / N+1 的取舍。
4. **等确认**：默认只讨论。你说“按这个拆 / 开始写”才写任务书；一句“行 / 可以”不算。
5. **写文档**：`00-总览.md` + 每个 P 一份 `P{n}-短名.md`，每份带状态、依赖、接口、验收、开工语、变更记录。
6. **处理问题**：你转告 P 的话或项目问题，它先读任务书和材料，判断是任务书问题、材料问题、接口冲突、执行问题还是范围变更；默认只改对应 P 的任务书，给你要转交的话。其他 P 的任务书、材料和代码不动。

## P 是什么

P 是一个独立开发会话（Parallel / Process），一份任务书，一组可独立验收的交付物。你手动新开会话，选合适的开发预设，把任务书里的开工语粘进去，P 就开始干活。

总控看不到 P 的对话，只能看到你转告的内容。所以：

- 开工语里要求 P 先复述理解，再动手；
- P 卡住 / 有歧义时，把 P 的原话、报错、复现步骤转给总控；
- 总控给你一段话，你转给对应 P；
- 任务书由总控维护，P 只读。

## 任务文档区

默认放在 `<项目根>/任务管理/`；如果把会话工作区直接设成任务文档区（推荐，见「安全边界」），任务书就写在工作区根，不再套一层 `任务管理/`。

```text
任务管理/
  00-总览.md          # 项目一句话、P 总表、依赖/波次、全局约定、待确认、变更记录
  P1-登录与账号.md     # 一个 P 一份任务书
  P2-房间与交互.md
  P3-联调与验收.md
```

- 任务书里用项目相对路径；P 会话工作区默认是项目根。开工语里的路径按 P 的工作区写，总控自己读写时按自己的工作区换算。
- 每份任务书自包含：P 只需要读自己这份 + 「开工前必读」里列的材料。
- 每份任务书都有编号、状态、版本和变更记录；改一次就 +1 版，写清触发和影响。
- 编号不重排：取消 / 合并保留编号，用状态标记；新增用下一个号。
- 已有任务文档区时先读，问你是继续、重建还是只补差异，不直接覆盖。

## 任务书里有什么

标题与状态/版本/模块/依赖/并行/验收方式 → 开工语 → 一句话目标 → 开工前必读 → 要做/不做/文件边界 → 需求与实现要点 → 交付物 → 验收标准 → 与其他 P 的接口 → 工作方式 → 汇报格式 → 变更记录。

需求写到 P 能判断“做完没有”；验收标准要可判定；接口没定就写“待定”并标 owner。不写实现代码。

## 开工语长什么样

```text
你是 P2，负责「房间与交互」。

先读任务书：`任务管理/P2-房间与交互.md`，再按「开工前必读」读材料；读完先向我复述：做什么、不做什么、交付物、验收标准、依赖谁、可能的风险，确认后再动手。

只做「要做」里的内容；「不做」的不要碰；范围外发现的问题记下来报告，不要顺手改。
不修改其他 P 的文件和任务书；共享文件/接口变更先停下来问。
任务书由总控维护，你不要改；需要改需求就报告，不要自己改文档。
完成后按任务书「汇报格式」汇报。
有歧义、缺材料、与现状冲突，先停，把具体问题和你的建议一起报给我。
```

## 项目出问题时

总控会先把问题分到五类里的一类，再决定动不动任务书：

| 类型 | 表现 | 总控做什么 |
|---|---|---|
| A 任务书没说清 | P 按任务书做，但结果不对 / 漏了边界 | 改对应 P 的任务书，补条件、边界、验收；给你转交的话 |
| B 材料矛盾 / 缺失 | 两份材料打架、关键设定没写 | 不改材料；在对应 P 任务书里记阻塞 / 待确认，给你选项 |
| C P 之间接口冲突 | 字段、时序、文件边界对不上 | 找 owner，改 owner 的任务书；给两边各一段话；另一份要改先问你 |
| D P 执行偏差 | 任务书没错，P 做错 / 没测 | 不改任务书（除非同类问题反复出现）；给你纠正 P 的话 |
| E 范围变更 | 新增 / 删减需求 | 先确认新范围，再改受影响 P 的任务书和总览 |

只改该改的那一份：

- 默认只改对应 P 的任务书；必要时更新总览的状态 / 变更记录。
- 其他 P 的任务书、项目材料、代码、P 的产出，一律不动。
- 跨 P 的改动先列影响，等你确认。
- 不改材料；即使问题根源在材料，也只给建议文本 / 标阻塞。

给 P 的话长这样（由你转交，总控不会直接发）：

```text
给 P3 的变更通知（2026-11-12）

问题：P3 的登录响应字段与 P2 提供的接口不一致。
结论：任务书接口契约写漏了，已更新 P3 任务书 v2 第 7 节。
任务书：任务管理/P3-登录接口.md，第 7 节，v2
现在做：
1. 按 P2 契约把字段改为 userId / token / expiresAt；
2. 补一条字段缺失时的错误分支；
3. 重跑登录相关自检。
不要做：不要改 P2 的文件；不要顺手重构其他接口。
验证：正常登录、字段缺失、token 过期三条路径。
回报：按任务书「汇报格式」回复；有歧义先停。
```

## 预设包含什么

| 能力 | 插件 | 说明 |
|---|---|---|
| 身份与流程 | `dsh-persona` | 上面那套总控规则 |
| 工作区指令 | `dsh-agent-instructions` | 读 `AGENTS.md` / `CLAUDE.md`，把执行约束摘进任务书 |
| 时间上下文 | `dsh-time-context` | 变更记录写准日期 |
| 文件读写 | `dsh-tool-fs` | `read` / `read_image` / `write` / `edit`；`apply_patch` 关闭；只应写任务文档区 |
| 目录与检索 | `dsh-tool-fs-search` | `glob` / `grep`，找材料和现有代码结构 |
| 提问 | `dsh-tool-ask-user` | 范围、拆分、确认、取舍 |
| 进度跟踪 | `dsh-tool-todo` | 读材料 / 拆 / 写文档多步跟踪 |
| 交付 | `dsh-tool-present` | 任务书作为卡片展示 |
| 上下文管理 | compaction / tool-result-pruner | 长会话不被上下文撑爆 |

刻意**没有**给：

- shell / pwsh / bash：总控不跑命令、不跑测试、不装依赖；这些是 P 的活。
- Office / PDF 解析技能：没有 shell 就执行不了 Python；二进制材料请导出为 md/txt 或贴关键内容，避免为了读文档引入命令执行面。
- web：判断依据是项目材料，不是网上的“通常做法”；需要外部资料时由你或 P 提供。
- subagent / workflow：任务分配给手动开的 P 会话，不绕过你直接派活。
- apply_patch：避免多文件补丁；任务书用 `write` / `edit` 单文件改。
- goal / schedule / plan mode：总控不应该自己长期跑，也不应该自己开工。

## 使用方法

1. 安装本目录为 bundle（已装的话跳过）。在插件管理器里对
   `E:\⭐模板库\预设库\project-manager-preset` 执行 `install_bundle`。
   手动方式：在 profile 的 `package.json` 里加依赖
   `"@local/dsh-project-manager-preset": "link:E:/⭐模板库/预设库/project-manager-preset"`，
   再把 `@local/dsh-project-manager-preset` 加到 `dsh.profile.bundles` 末尾，最后在该 profile 目录跑一次 pnpm。
2. 刷新 Web 界面，新建会话，在预设选择器里选 **总控**。想要物理隔离，就先把 `<项目根>\任务管理` 建好，再把新会话的工作区设为它、权限设为 `workspace-write`；否则按项目根模式用。
3. 正常开聊，比如：

   ```text
   项目在 E:\创作项目\水暖's。先读策划案、交互与视觉设计案、技术需求案，别改任何文件；读完告诉我模块和不清楚的地方。
   ```

   ```text
   按推荐的 5 个 P 拆，任务书放任务文档区，开始写。
   ```

   ```text
   P3 说登录接口和 P2 的字段对不上，这是 P3 的原话：…… 你判断该改谁的任务书，给我转给 P3 的话。
   ```

   ```text
   把 P3 任务书第 6 节的验收标准补上 token 过期，其他 P 的不要动。
   ```

4. 想先讨论、不落文件，就直说“先别写”；想让它动笔，必须说“按这个拆 / 开始写”。它会把“行 / 可以”当成认可，不是指令。

## 安全边界（说清楚）

- **默认靠预设约束，不是沙箱**：工作区=项目根时，总控没有 shell，也没有 `apply_patch`，写入只应发生在任务文档区；但 DSH 当前的 `write` / `edit` 不能按路径白名单拦截。预设把“只写任务文档区”写成硬规则，靠模型遵守。想要物理隔离，用下面那条。
- **想要更硬的隔离**：把会话工作区设在任务文档区（例如 `项目根\任务管理`），材料用绝对路径读，权限用 `workspace-write`。这样沙箱只允许写工作区，材料在区外，物理上改不了。注意：沙箱只认工作区根，不认“工作区里的某个子目录”。总控会先确认你用的是哪种工作区模式，不会把任务文档区误当项目根。
- **材料永久只读**：即使你口头允许，它也不改材料、代码、P 的产出；要改材料，它只给建议文本，由你或材料负责人动手。
- **二进制材料**：docx/xlsx/pdf 的正文读不了；请导出 md/txt 或贴关键内容。这是为了让预设没有命令执行能力。
- **不做验收**：它定义验收标准，但不判定通过；最终验收用「项目验收」预设或人工。
- **一个项目一个总控会话**：两个总控同时改任务书会打架；改之前它应该先读最新版本。

## 修改与卸载

- **改行为**：编辑 `cordis.patch.yml` 里 persona 的文案、任务书骨架或插件清单。这个 bundle 是本地 `link:` 依赖，改完通常会被文件监听重新组合；没生效就刷新页面或重启应用。
- **改任务文档约定**：改 persona 第七节和 README 的「任务文档区」；已经写出的任务书不会自动改，需要按新约定迁移。
- **卸载**：在插件管理器里移除 `@local/dsh-project-manager-preset`；如果手动装过，再从 profile 的 `package.json` 删除依赖和 `dsh.profile.bundles` 条目，并重跑 pnpm。
- **注意**：本目录是安装源，**不要删除、移动或改名**，否则预设会从列表里消失。

## 注意

- 预设只影响**新建**会话；已经开着的会话保持原来的预设。
- docx/xlsx/pdf 请先导出为 md/txt；本预设不装依赖、不跑转换。
- 总控看不到 P 的对话；P 的问题要由你转告，最好带原话、报错、复现步骤。
- 任务书是唯一的事实来源；你手动改过任务书后，让总控先重读再继续。
- 一个会话只管一个项目；换项目就新开一个总控会话。
